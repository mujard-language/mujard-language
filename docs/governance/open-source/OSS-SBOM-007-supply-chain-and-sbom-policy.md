# OSS-SBOM-007 Supply Chain and SBOM Policy

- Policy ID: OSS-SBOM-007
- Classification: Internal
- Status: Draft pending approval
- Owner: Open Source Governance
- Version: 1.0

## 1. Purpose

This policy defines how Mujard tracks its dependencies, produces a Software
Bill of Materials for releases, and keeps the toolchain supply chain pinned
and verifiable.

It extends the dependency rules in `docs/OPEN_SOURCE_ADOPTION_PLAN.md` to the
open-source components themselves.

## 2. Dependency inventory

The project already keeps three inventories that together cover the supply
chain:

- `docs/THIRD_PARTY_LICENSES.md` — generated by `tools/licenses/generate.php`
  from the PHP, web, Android and desktop dependency trees. It is the license
  inventory and the seed for the SBOM's third-party section. It is regenerated
  whenever a dependency is added or updated.
- `toolchain/index.json` (`mujard-toolchain-index.v1`) — every downloadable
  toolchain package with version, license string, source URL and per-system
  sha256 and size. `mujard-build` verifies the sha256 before installing to
  `%LOCALAPPDATA%\mujard\toolchains`.
- `tools/mujard/go.mod` — the Go module dependencies of the CLI/compiler
  (currently the pinned `golang.org/x/mobile` toolchain set used for the
  Android binding build).

Board manifests (`toolchain/boards/*.json`) and package descriptors
(`toolchain/packages/*.json`) are first-party data, not third-party
dependencies, but they reference the pinned packages above.

## 3. SBOM requirement

- Every public release of the compiler/CLI (OSS-REL-006) ships an SBOM
  covering the released artifacts: the Go binaries, the runtime sources, the
  board/toolchain definitions and the bundled third-party notices.
- Format: CycloneDX JSON is the default; SPDX JSON is acceptable where
  tooling produces it more reliably. The format choice is recorded in the
  release notes.
- The SBOM is generated, not hand-written: the inventory sources in section 2
  are the inputs, and the generation step is added to the release checklist
  (OSS-REL-006 section 4) once tooling is chosen.
- The SBOM lists components with name, version, license (SPDX id where known)
  and hashes where available; UNKNOWN or flagged licenses must carry a written
  decision, matching the "Needs a decision" discipline already in
  `docs/THIRD_PARTY_LICENSES.md`.

## 4. Toolchain supply chain

Already in place and kept:

- Every third-party toolchain download is pinned by sha256 in
  `toolchain/index.json`; verification happens at install time. New packages
  enter only as sha256-verified downloads.
- Toolchains are installed outside the repository
  (`%LOCALAPPDATA%\mujard\toolchains`), so the repo never vendors binaries.
- The Arduino-derived cores the generated firmware links against (for
  example the AVR core under LGPL-2.1, the avr-gcc toolchain under
  GPL-3.0-or-later with the GCC runtime exception) are downloaded by the
  user's toolchain install, not redistributed by Mujard — their licenses
  travel with them per their own terms. This boundary is deliberate:
  Mujard-generated firmware is the user's artifact; the cores it links are
  the user's toolchain choice, recorded in the SBOM.

## 5. License compatibility rules (unchanged)

Per `docs/OPEN_SOURCE_ADOPTION_PLAN.md`:

- Prefer MIT, BSD, Apache-2.0; MPL-2.0 acceptable; GPL/AGPL only as separate
  unmodified programs.
- Never adopt BSL, SSPL, Elastic License, Commons Clause or source-available
  licenses for anything we build on.
- Shipped copies carry the component licenses and notices (the `/licenses`
  web page and the Android "Open source licences" screen already do this;
  OSS-LIC-002 governs the open components' own notices).

## 6. Provenance goals

Current state: local git history, DCO sign-off on contributions,
sha256-pinned toolchain downloads, generated license inventory.

Planned, in order:

- SBOM per release (section 3).
- Build provenance: record the Go/toolchain versions and the
  language-update run that produced each binary in the release notes.
- Reproducible-ish builds: document the build environment (the repository's
  toolchain table is the current record) so a second machine can reproduce
  `MujardCLI.exe`.
- Artifact signing when key infrastructure exists (OSS-REL-006 section 7).
- With the public remote: CI that runs the same `go test ./...` and
  `go vet` gates on every pull request, so the SBOM's inputs are continuously
  verified rather than only at release time.

## 7. Vulnerability intake

Known-vulnerability handling for dependencies is part of OSS-SEC-008: reports
against the open components go to the private channel; dependency updates
that fix advisories are PATCH releases with changelog entries naming the
CVE/GHSA where public.
